# OpenCode v2 baseline: migration and compatibility status

## Active setup

- Target CLI rechecked as OpenCode `v2.0.22` (`opencode --version`). The live managed bundle link was created via `./install --only link` before the Dotbot wrapper was restored unchanged. Going forward, the general Dotbot config pass excludes OpenCode; use `scripts/install-opencode.sh` for guarded activation. Neither script installs or replaces the OpenCode executable.
- Before activation, the live config directory was verified empty. Bootstrap retained that empty directory at `~/.local/share/dotfiles/opencode-backups/20261003-123656.4ylF90` (manifest records `opencode v2.0.22` and the executable path). This is a fresh-config backup, **not** a backup of the earlier lost v1 tree.
- OpenCode reports config at `~/.config/opencode`, data at `~/.local/share/opencode`, state at `~/.local/state/opencode`, cache at `~/.cache/opencode`, and its session database at `~/.local/share/opencode/opencode.db` (`opencode debug paths`). Bootstrap manages only the config directory; it does not move or rewrite the separate data/state/cache trees.
- The managed configuration is intentionally non-secret. It leaves OpenCode's built-in `explore` subagent permissions unchanged and configures an 8,000-token compaction retention value while disabling ordinary automatic compaction. A model-window-aware 50% trigger is **not implemented**; disabling the competing fixed/default trigger avoids claiming that behavior is present.
- The isolated v2 smoke test starts the installed CLI's server using copied assets, private HOME/XDG/TMP directories, and a cleared credential environment. On the active install, `opencode debug config` identifies the managed JSON as a loaded config source and normalizes compaction retention to 8,000 tokens. `opencode debug agents` confirms the built-in `explore` exists; no custom permissions are configured. Its default table includes a wildcard allow, so its read-only system prompt is not a hard read-only policy. This proves the compaction setting loads, but not strict rejection of unknown schema keys or runtime compaction behavior. A `/skill` API probe resolved to the web UI rather than a skill-list response, so skill and AGENTS instruction loading remain unverified. `opencode plugin list` reports no plugins. TUI/footer behavior and actual compaction behavior were not tested.

## Assets and compatibility

- The 29 Pi skill directories and 62 total files (29 `SKILL.md` files plus 33 supporting files) are copied under `.config/opencode/skills/`; they contain no symlinks back to Pi. The copied setup-context skill includes its relative helper/reference files, and its session-claim examples are adapted to OpenCode-neutral identifiers. No ongoing synchronization is used.
- `.config/opencode/AGENTS.md` is the intended global instruction file. It uses OpenCode terminology and explicitly warns against Pi-only integrations. Loading was **not** observably verified against v2.0.22 in this pass.
- No Pi extension is copied or loaded as an OpenCode plugin. In particular, the Pi RTK command-rewrite extension is not active; a v2-compatible equivalent has not been built or verified.
- No Pi model/provider/reasoning defaults are configured. `opencode models` lists `openai/gpt-6.1-sol`, `opencode-go/qwen3.8-flash`, and `opencode-go/glm-5.3-flash`; it does **not** list the Pi provider ID `openai-codex`. `opencode auth list` listed no credentials for `openai`, `openai-codex`, or `opencode-go`. Model IDs are therefore catalog-visible, but provider authentication and reasoning-variant compatibility are unverified; no defaults are silently selected.
- `cli.json` selects OpenCode's `catppuccin` theme by name, but availability/rendering was not verified and no custom palette/theme asset or footer adapter was delivered. The directory/branch display, Dumb-zone boundaries and meter, small-model clamp, usage refresh, missing-metadata display, and plugin cleanup remain unimplemented and unverified.
- Native questions/todos/subagents/LSP/web behavior were not exercised at the installed-runtime boundary. Built-in `explore` defaults are left untouched; its wildcard permission means read-only behavior is prompt-level, not enforced by this config. Tool discovery, Pi codemode, extraction-model selection, concurrency, and model-preset cycling remain compatibility questions rather than claimed parity.

## Migration and recovery

- At the post-incident recheck, `~/.config/opencode` contained no config files; the managed setup therefore starts fresh. The prior v1 configuration tree had been moved into a temporary test sandbox whose cleanup removed that copy. No Time Machine backup was found. The old config-tree skills/plugins/custom `ctx` and any credentials stored there may be unrecoverable. This was **not** a successful backup or preservation of that tree.
- The separate OpenCode data, state, cache, and session database locations above were left in place and were not migrated or downgraded. Pi's tracked configuration was not edited.
- Bootstrap keeps config backups under `${XDG_DATA_HOME:-~/.local/share}/dotfiles/opencode-backups/`. The active backup above contains only the empty directory that existed at activation; it cannot restore missing historical files. For a future backed-up config, use `scripts/migrate-opencode.sh restore <backup-directory>` when the target path is absent or is the managed symlink. Database rollback is not attempted.
- To deactivate this fresh managed link, remove `~/.config/opencode` (first verify it points to this repository); restoring the retained empty directory creates an empty config, not the missing former setup. The migration contract tests cover existing-config backup/rollback, fresh setup/rollback, failure safety, custom-XDG refusal, Dotbot exclusion, and idempotent guarded activation.

## Verified versus unresolved

Verified: exact CLI version and reported state paths; the config source and normalized compaction setting load; the three preferred model IDs (with provider-name caveat) appear in the catalog; no auth entries/plugins are listed; independent copied-skill tree; Dotbot leaves OpenCode untouched, while the dedicated guarded installer is sandbox-tested for idempotence and migration rollback/failure cases; and isolated v2 server startup without production credentials.

Unresolved: active instruction/skill discovery, v2.0.22 plugin integration and footer/theme behavior, provider authentication and reasoning-variant compatibility, native workflow semantics, RTK, model-aware automatic compaction, and interactive UI verification. This is a **partial fresh baseline**, not full Pi parity; do not infer those features from successful server startup.
