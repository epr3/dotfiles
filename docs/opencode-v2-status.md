# OpenCode v2 baseline: migration and compatibility status

## Active setup

- Target CLI rechecked as OpenCode `v2.0.22` (`opencode --version`). The live managed bundle link was created via `./install --only link` before the Dotbot wrapper was restored unchanged. Going forward, the general Dotbot config pass excludes OpenCode; use `scripts/install-opencode.sh` for guarded activation. Neither script installs or replaces the OpenCode executable.
- Before activation, the live config directory was verified empty. Bootstrap retained that empty directory at `~/.local/share/dotfiles/opencode-backups/20261003-123656.4ylF90` (manifest records `opencode v2.0.22` and the executable path). This is a fresh-config backup, **not** a backup of the earlier lost v1 tree.
- OpenCode reports config at `~/.config/opencode`, data at `~/.local/share/opencode`, state at `~/.local/state/opencode`, cache at `~/.cache/opencode`, and its session database at `~/.local/share/opencode/opencode.db` (`opencode debug paths`). Bootstrap manages only the config directory; it does not move or rewrite the separate data/state/cache trees.
- The managed configuration is intentionally non-secret. It leaves OpenCode's built-in `explore` subagent runtime toolset untouched (read-only at the tool level, verified in ticket `0003` via `scripts/test-opencode-workflows.sh`), configures native `compaction.keep.tokens: 8000`, disables the competing native automatic threshold, sets the root default model to `openai/gpt-6.1-sol` (Pi's default model after catalog validation; the Pi `medium` reasoning level is not encodable as a root default in v2.0.22), and pins subagent model/reasoning preferences under `agents` (`explore` = `opencode-go/qwen3.8-flash` variant `low`, `general` = `opencode-go/glm-5.3-flash` variant `high`). Ticket `0005` adds a v2 server plugin that checks the newest assistant message and its advertised model window after successful execution, then requests native compaction at or above 50% of that window; it skips missing capacity metadata. The post-execution event is a safe scheduling point and native `keep.tokens` applies to the requested compaction. The isolated runtime verifies below/at/above boundaries for a 128k fixture window. Runtime coverage for a second window and model switching remains incomplete because the v2.0.22 public prompt API used by the deterministic fixture ignores per-message model overrides; pure policy tests cover a second 512k window but do not substitute for that runtime evidence. Provider overflow-recovery behavior with `auto: false` is not claimed or verified.
- The isolated v2 smoke test starts the installed CLI's server using copied assets, private HOME/XDG/TMP directories, and a cleared credential environment. On the active install, `opencode debug config` identifies the managed JSON as a loaded config source and normalizes native `compaction.keep.tokens` to 8,000 tokens. `opencode debug agents` confirms the built-in `explore` exists; no custom permissions are configured. Its default table includes a wildcard allow, so its read-only system prompt is not a hard read-only policy. This proves the retention setting loads, but not strict rejection of unknown schema keys or runtime compaction behavior. An early `/skill` API probe resolved to the web UI rather than a skill-list response, so skill and AGENTS instruction loading were unverified in that pass; both are now verified through the `skill.list`/skill-injection API and a captured prompt in `scripts/test-opencode-assets.sh`. `opencode plugin list` reports no plugins. TUI/footer behavior and actual compaction behavior were not tested.

## Assets and compatibility

- The 29 Pi skill directories and 62 total files (29 `SKILL.md` files plus 33 supporting files) are copied under `.config/opencode/skills/`; they contain no symlinks back to Pi. 18 skills are byte-identical copies; 11 carry narrow adaptations for OpenCode vocabulary and harness-neutral paths (notably the `setup-context` helpers, session-claim identifiers, and global-instruction home), preserving triggers, prerequisites, and invocation intent. No ongoing synchronization is used. The full disposition is recorded in `docs/opencode-v2-asset-inventory.md`; `scripts/test-opencode-assets.sh` checks the copied tree both statically and at the isolated runtime boundary.
- `.config/opencode/AGENTS.md` is the global instruction file. It uses OpenCode terminology, rewrites Pi tool names to native equivalents, and warns against Pi-only integrations. Loading through the supported v2 `AGENTS.md` mechanism — not the accepted-but-unresolved `instructions` config array — is verified in `scripts/test-opencode-assets.sh` by capturing the assembled prompt from a local mock provider.
- No Pi extension is copied or loaded as an OpenCode plugin. The Pi RTK command-rewrite extension was assessed in ticket `0003` and replaced by a purpose-built v2 plugin at `.config/opencode/plugins/rtk.ts` (thin delegation to `rtk rewrite` with Pi semantics: version floor 0.23.0, `RTK_DISABLED`, 2s timeout, fail-open, exit-code 0/3 rewrites); the canonical RTK v1/Pi plugin is not activated unchanged.
- No Pi model/provider/reasoning defaults were configured at the `0002` checkpoint; ticket `0003` validated the preferred combinations against the live catalog and configured them: the managed bundle now sets the root default `openai/gpt-6.1-sol` (Pi's `openai-codex` provider ID does not exist in the catalog; the same model ID exists under the authenticated `openai` provider), `agents.explore` = `opencode-go/qwen3.8-flash` variant `low`, and `agents.general` = `opencode-go/glm-5.3-flash` variant `high` (both catalog-listed with those variants; OpenCode Go auth stored). Pi's `medium` default reasoning level is not encodable as a v2 root default in 2.0.22 (root `model` cannot retain a `#variant`; a bare agent `variant` is inert) — reported with the per-session `--model provider/model#variant` mitigation instead of silent substitution. Unavailable preferred combos (e.g. a reasoning level on `opencode-go/kimi-k2.7-code`, which has no variants) are reported explicitly in `docs/opencode-v2-workflows.md`.
- `cli.json` selects the built-in `catppuccin` theme by name; the footer adapter consumes OpenCode's resolved theme tokens rather than a copied Pi palette, so no Pi theme file is copied (verified selectable at the isolated runtime boundary). The themed dumb-zone footer itself is ticket `0004` and is now delivered at `.config/opencode/plugins/dumb-zone/` (see its report below).
- No Pi extension is copied or loaded as an OpenCode plugin; native questions/todos/subagents/LSP/web capabilities were exercised at the installed-runtime boundary in ticket `0003` (`scripts/test-opencode-workflows.sh`). Built-in `explore` is hard read-only at the runtime — its mutating tools are absent from the child toolset regardless of configuration; the managed `agents` config additionally carries `edit`/`shell` deny rules as defense against future built-in changes. Tool discovery, web extraction-model selection, subagent concurrency, and model-preset cycling are reported gaps without custom equivalents; Pi's codemode maps to v2 native Code Mode (primary agents only), and there is no native todo tool or agent-facing LSP toolset in v2.0.22. Details: `docs/opencode-v2-workflows.md`.

## Dumb-zone statusline (ticket 0004)

- The themed dumb-zone footer is delivered as a v2 CLI plugin at `.config/opencode/plugins/dumb-zone/` (`zone.ts` pure contract, `segments.ts` pure footer assembly and host-shape readers, `tui.tsx` host adapter), registered in `cli.json` as `./plugins/dumb-zone`. It claims the `prompt.footer.status` slot and renders `directory │ ⎇ branch │ ◑ RISKY ██████░░░░ 65% eff · 130k/200k · 33% nom` — directory basename, git branch, zone glyph/label, a ten-cell effective-budget meter and percentage, token usage, and the nominal-window percentage — exactly the deployed contract of the ADR: fixed 200,000-token effective limit, sharp/fading thresholds at thirds, risky below the limit, and the inclusive Caveman boundary at or over it; the limit clamps down to smaller advertised windows and never scales up for larger ones. The boundary suite pins both sides of every default third stop so the fractional comparisons cannot drift.
- Override precedence preserves the deployed layering in OpenCode terms: code defaults (the 200k contract) < managed plugin options (the `cli.json` plugins object form — the managed/user layer, with Pi's `effectiveLimit`/`thresholds`/`meterWidth` key shape) < environment (`EFFECTIVE_LIMIT` with k/M suffixes, `Z_SHARP`, `Z_FADING`, `Z_RISKY`). The managed registration passes no options today, so the contract defaults are what runs; the object form is how managed tuning would be encoded. Pi's separate global/project settings files have no per-project settings mechanism here beyond the managed bundle; env remains the quick-experiment layer.
- Colors come from OpenCode's resolved theme tokens (`text.muted`, `text.feedback.success/warning/error.base`) — the adapted compatible palette for the `catppuccin` selection, with no Pi theme loading and no Pi runtime extension imported (attribution in `.config/opencode/CREDITS.md` records the MIT prior art used for the host-API patterns).
- The usage read is the newest assistant message's own token record (input+output+reasoning+both cache sides) — the session record's totals are cumulative across turns and would fabricate over-limit numbers; the nominal window is the active model's `limit.context` from the location model catalog. Missing usage or window renders `○ awaiting context` rather than zeros or percentages; a location outside a git repository omits the branch and keeps the directory.
- Refresh wiring: `session.step.ended`, `session.execution.*` (also refreshes the branch), `session.idle`, `session.model.selected`, and `session.compaction.ended` bump a reactive version signal; model selection is also read reactively. The setup returns a cleanup that stops every subscription; slot contributions are removed through normal slot cleanup when the plugin deactivates.
- Classification is display-only: the plugin subscribes to nothing that triggers compaction, mutates no configuration, and hooks no tools or responses.
- Verification: `scripts/test-opencode-statusline.sh` — static independence/registration/display-only checks, the bun boundary suite (48 tests: values immediately around each third, exactly 200,000, above the limit, small-model clamping, threshold and limit overrides through the managed and environment layers, honest unavailability, meter rounding, exact footer text), and an isolated-runtime probe that boots the real CLI into a fixture session and asserts the plugin's setup completes, the awaiting-context placeholder renders, no zone label or percentage appears before usage exists, and no failed plugin generation is logged. The live usage-cluster render and the interactive visual smoke (placement, readability, theme, updates) require real provider usage and a human at the terminal; per the ticket they are recorded for the activation ticket `0007`.

## Migration and recovery

At the post-incident recheck, `~/.config/opencode` contained no config files; the managed setup therefore starts fresh. The prior v1 configuration tree had been moved into a temporary test sandbox whose cleanup removed that copy. No Time Machine backup was found. The old config-tree skills/plugins/custom `ctx` and any credentials stored there may be unrecoverable. This was **not** a successful backup or preservation of that tree.

The separate OpenCode data, state, cache, and session database locations above were left in place and were not migrated or downgraded. Pi's tracked configuration was not edited.

Bootstrap keeps config backups under `${XDG_DATA_HOME:-~/.local/share}/dotfiles/opencode-backups/`. Ticket `0006` hardened this into a tested, repeatable migration contract (`scripts/migrate-opencode.sh`, `scripts/install-opencode.sh`, `scripts/test-opencode-migration.sh`):

- **Discovery over guessing.** Every existing-config backup manifest now records the installed executable's path and version (`previous-executable`, `previous-version`), the evidence source (`discovery=opencode-debug-paths`, or `unavailable` when the CLI is missing), and the tool-reported config/data/state paths plus cache, binary-cache, session-database, and session-storage rows. Credential stores (`auth.json` in the config and data directories) are recorded **by location only** — presence or `not-found`; contents are never read and never appear in backups or manifests. `data-path`/`state-path` fall back to the conventional XDG locations when discovery is unavailable, and no migration decision depends on the discovered rows: only the config directory is replaced.
- **Replacement, not merge.** Activation moves the whole prior config tree into a new manifest-verified backup directory, then links the managed bundle. The fixture suite demonstrates a v1-style config (`skills/legacy-rtk`, `plugins/legacy-rtk.js`, v1 credentials/session sentinels) migrating cleanly: the active collection ends up with no unmatched legacy skill or legacy plugin file, both survive in the backup, and `docs/opencode-v2-workflows.md` records that the legacy RTK plugin's unchanged form is never activated (its v2 equivalent at `.config/opencode/plugins/rtk.ts` is the supported disposition).
- **State preservation.** The fixture data tree (`opencode.db`, `auth.json`, `storage/sessions/`) is byte-identical across every migration, rollback, activation, and repeat cycle in the tests; backups, caches, session databases, credential stores, and node_modules/lockfiles stay out of tracked assets (asserted with `git check-ignore` and backup-root containment).
- **Repeat safety.** Every invocation creates its own timestamped backup directory: the fixture suite runs several full cycles and asserts earlier backups and their manifests are never overwritten; guarded re-running on an already-managed link is a no-op with no new backup.
- **Failure paths.** Backup-creation failure aborts before anything is replaced (prior config intact); a forced activation failure (`ln` refuses) rolls the byte-identical prior config back into place, retains the backup, clears the pending marker, and exits non-zero; rollback and `restore <backup-dir>` restore the backed-up tree (copy verified against the backup before it is activated) while the first backup is retained, not consumed. Use `scripts/migrate-opencode.sh restore <backup-directory>` when the target path is absent or is the managed symlink; to deactivate the fresh managed link, remove `~/.config/opencode` after first verifying it points to this repository. Custom `XDG_CONFIG_HOME` paths that the Dotbot link configuration does not manage are refused.
- **Executable selection and databases.** The scripts never install, remove, or replace the `opencode` executable; the manifest records the prior executable path and version so re-selecting an older release (if ever needed) is an explicit, machine-local developer action rather than a hidden side effect. Rollback and restore deliberately do not touch `opencode.db`: a database after v2 sessions has not been shown to be safely in-place downgradable, so recovery from that state requires restoring a machine-local database copy rather than assuming the old executable will accept it. No such downgrade is attempted or implied by these scripts.
